# 为什么需要 Ops Vibe Coding

## 问题

运维工程师通常很清楚业务痛点，却未必能一次性写出完整 PRD、前后端架构和测试计划。直接让 Agent “做一个平台”，常见结果是界面模板化、架构由 UI 脑补、危险操作缺少授权审计，最后只有“代码生成完成”，没有可复现的验收证据。

## 方法

Ops Vibe Coding 把工作拆成三类逐步收敛的契约：

1. Prototype 确认用户如何使用；
2. Architecture 确认系统由什么组成；
3. Spec 确认系统精确怎样工作和验证。

之后以纵向 Ticket、TDD、代码审查、运维就绪审查和真实浏览器 E2E 建立证据链。

## Operations-first 的含义

运维工具往往能删除资源、重启服务、执行命令或访问生产数据。因此以下问题不能等到上线前才处理：

- 谁可以执行什么操作，作用范围是什么；
- 操作是否可审计、可取消、可重试、可恢复；
- Secret、Token、SSH 或 Kubernetes 凭证如何保存；
- 外部系统不可达、任务重复执行或进程重启时会发生什么；
- 日志、数据、备份和结果保留多久；
- 部署、回滚、健康检查和资源限制是否明确。

Operations-first 不等于默认使用复杂基础设施。只读 Dashboard 和 200 台主机的批量远程执行具有不同风险，审查深度和组件组成必须由证据决定。

## 成功标准

第一版成功不是生成最多代码，而是让用户能够从一个模糊想法一路走到：

```text
可体验的产品意图
+ 已确认的运行约束
+ 可测试的规格与实现
+ 运维风险证据
+ E2E 报告
+ 人工最终验收
```
